## Built

- **`UnifiedMemoryStrategy`** (`bytelanes-wgpu/src/unified.rs`, agent C's
  module).
  - Inputs: a buffer is created mapped (`MAP_WRITE`), filled through the
    mapping, then unmapped.
  - Results and `Vram` buffers are allocated with `MAP_READ`, and `download`
    maps the result buffer itself.
  - wgpu's Metal backend puts every buffer with `MAP_READ` or `MAP_WRITE`
    in `MTLStorageModeShared`, and mapping one returns the buffer's own
    pointer with no copy. Source: wgpu-hal 30.0.2, `metal/device.rs`,
    `create_buffer` and `map_buffer`.
  - It needs `Features::MAPPABLE_PRIMARY_BUFFERS`, which Metal offers.
    `for_adapter` refuses an adapter that is not an integrated GPU or lacks
    that feature, so a discrete GPU cannot pick it by mistake.
  - Result and device buffers get `MAP_READ` only. Metal makes `MAP_WRITE`
    memory write-combined, which is slow for the CPU to read.
  - A buffer without `MAP_READ` falls back to the copying download.
- **Two hooks on `BufferStrategy`**, both with defaults, so
  `CopyingStrategy` behaves exactly as before:
  - `required_features`: requested when the device opens.
  - `alloc`: every op result and `Vram` buffer.

  To use them, two lines in agent B's `gpu.rs` changed: `Gpu::new` requests
  `strategy.required_features()`, and `Gpu::zeroed` calls
  `strategy.alloc`. No shader changed.
- **Tests:**
  - `tests/common` now opens each adapter once per applicable strategy, so
    `conformance.rs` and `large.rs` run both strategies on the Mac. On
    discrete GPUs (the Ryzen) nothing changes, because the unified strategy
    does not apply.
  - `tests/unified.rs`: byte-exact round trips at unaligned offsets and odd
    lengths, the fallback path, mapping after GPU work, and refusal of
    non-unified adapters.
- **`strategy_cost` example.** Times upload, download, and whole
  host-to-host Checksum and Decrypt programs per strategy, from 4 KiB to
  1 GiB. Every sample is kept, and the output is an atlas run file.
- **Docs:** README (buffer strategies section), CHANGELOG (Unreleased),
  CLAUDE.md layout line.

### What "zero-copy" means here

On the unified path:

- The GPU computes on the input buffer the CPU filled.
- The CPU reads the result from the buffer the GPU wrote.
- There is no GPU copy and no staging buffer in either direction.

One CPU copy per direction remains, because the backend's host buffers are
`Vec<u8>`. Inputs are copied into the shared buffer, and results are copied
into the `Vec`. Removing those two copies needs one of:

- **The GPU working on the caller's own memory.** On Metal that is
  `newBufferWithBytesNoCopy`. wgpu 30 reaches it only through
  `Device::create_buffer_from_hal` and `wgpu-hal`'s `buffer_from_raw`,
  which are `unsafe`, and this repo forbids `unsafe`. This is the gate's
  "not possible in current wgpu" case for true zero-copy from caller
  memory.
- **Host buffers backed by GPU buffers.** This is possible without
  `unsafe`, but it is a larger change to agent B's `backend.rs`. wgpu also
  forbids GPU use while a buffer is mapped, so each host-side access would
  need a map and an unmap. Not done; question 2.

1. **Transfers alone: unified is cheaper at every size, and the p10–p90
   ranges never overlap.**
   - Downloads are 5 to 246 times cheaper.
   - Uploads are 1.15 to 6.9 times cheaper.
   - The large-size upload cost is mostly a new 1 GiB allocation, which
     wgpu zero-fills, then the copy. A pool of reused shared buffers might
     remove most of it. That is untested; see question 3.
2. **Whole programs: no consistent gain from 1 MiB to 1 GiB (a negative
   result).**
   - Unified is 1.4 to 1.8 times faster at 4 to 64 KiB.
   - From 1 MiB up the two are within noise of each other. Medians go both
     ways, from 0.69 to 1.10. Several series are bimodal: the median sits
     at one of two levels about 0.4 ms apart, as at 1 MiB above.
   - Transfer cost is not what limits a program here. Agent B's M3 status
     says the backend submits and waits on every step of a program. A
     ~0.5 ms floor per program fits that, but I did not measure it
     separately.

     between levels, both with shared and with private intermediate
     buffers. So shared memory is not the cause.

## A bug found on the way: GPU CRC-32C wrong from 512 MiB

The first recorded run stopped at a 1 GiB Decrypt with `CrcMismatch`.

- **Cause:** `tables.rs` `crc_byte_powers` wrapped its index with
  `(k + 3) & 31`, assuming `x^(2^n) mod P` repeats every 32 steps. That
  holds for zlib's CRC-32 polynomial. For CRC-32C the period is 31, checked
  numerically. So table entries 29 to 31, used for lengths of 2^29 bytes
  and more, were wrong.
- **Effect, on every GPU and API, not only Metal:**
  - `Checksum` over 512 MiB or more returned a **wrong value with status
    `Ok`**. The receiver cannot catch this: the completion CRC covers only
    the 4 output bytes, and those verify. Confirmed at 512, 768, 1023 and
    1024 MiB against `cpu::ops::checksum`.
  - Any result of 512 MiB or more failed its completion CRC check. The
    decrypted bytes themselves were correct.
- **Why the tests missed it:** M3's largest CRC case is 96 MiB, and the
  random cases are 4 KiB or less.
- **Fix:** commit `dbfc5f8`, host code only, no shader. The table is built
  by repeated squaring with no wrap.
  - A unit test checks each entry is the square of the one before.
  - A new large test runs Checksum and Decrypt over 600 MiB.
  - Both tests fail on the old table and pass on the new one, on Metal with
    both strategies.

This is agent B's code. I fixed it rather than only reporting it because
it is a one-function host-side fix and it blocked the gate measurement.
Agent B should review it and run the large test on Vulkan and DX12
(Requests).
