## Built

- **`WgpuBackend`** (`bytelanes-wgpu`, wgpu 30.0.2) implements
  `bytelanes::ChannelBackend` and `bytelanes::Buffers`.
  - **Status checks** run on the host in exactly the order `CpuBackend`
    uses: validation, op, extent kinds, buffers and bounds, key, length,
    destination size. Both backends therefore report the same status, command
    index and byte count for any program.
  - **All work on the data runs in WGSL:** the op itself, writing a result
    into device memory at any byte offset, and the CRC-32C of every result
    (spec rule 5).
  - **Ordering:** programs run in order on a worker thread, so `submit` and
    `poll` never wait for the GPU.
- **Kernels:**
  - **Checksum (CRC-32C):**
    - Each thread computes the raw CRC of one 256-byte chunk with a byte
      table.
    - A tree of passes combines neighbouring chunks by multiplying by
      x^(8·len) mod P. This is zlib's `crc32_combine` method.
    - A last pass folds in the initial value and the final xor.
    - Inputs may start at any byte offset.
  - **Encrypt and Decrypt (AES-256-CTR):**
    - One thread per 16-byte block.
    - The round table and S-box sit in workgroup memory.
    - The counter is a 128-bit big-endian add that wraps at 2^128.
    - The key schedule is computed on the host when a key is loaded, and is
      tested against FIPS-197 A.3.
  - **Filter:**
    - Each element becomes an integer key that sorts like the value:
      - -0.0 becomes +0.0.
      - Negative floats have all their bits flipped.
      - Every other value gets its sign bit set.
      - NaN is a separate flag.
    - Because everything is integer arithmetic, NaN, signed zero and
      subnormals follow IEEE 754 whatever the GPU's float hardware does.
      `u64`, `i64` and `f64` are handled as pairs of `u32`, as you decided
      in M1.
    - Count, scan and scatter passes write indices in ascending order.
  - **Place:** writes a result into a Vram buffer at an unaligned offset.
    Each thread owns one destination word, so no atomics are needed.
- **`BufferStrategy` trait and `CopyingStrategy`.** This is how host bytes
  reach the GPU and come back, and it is the seam for agent C's
  unified-memory strategy in M4. The ops only ever see a `wgpu::Buffer`.
- **Other additions:**
  - `hardware_adapters()`, which honours `WGPU_BACKEND`.
  - The `adapters` example.
  - `WgpuBackend::clear()`, which gives each golden case an empty backend
    without reopening the device.
- **Tests:**
  - `tests/conformance.rs`: every golden vector, then 10,000 random cases
    per op, on every hardware adapter.
  - `tests/large.rs`, ignored by default: inputs of hundreds of MB.
  - Unit tests for the tables, the chunked CRC math and the order keys.
- **Docs:** README, changelog (Unreleased) and CLAUDE.md updated. No version
  bump; that comes in M5.

The large-input cases reach code paths that the random cases, at 4 KiB or
less, cannot:

1. CRC-32C of 96 MiB at byte offset 1, which goes through 19 combine levels.
2. AES-256-CTR decrypt of 96 MiB with the IV set to all `FF` bytes. It needs
   more than 65,535 workgroups (a 2D grid), and the counter wraps at 2^128
   on the first block.
3. A 32 MiB encrypt into Vram at offset 5, chained into a checksum.
4. A `u32` Filter over 70 million rows: 68,360 tiles, so both a 2D grid and
   a scan longer than one workgroup.
5. An `f64` Between filter over 8 million rows.

Every case was compared with `CpuBackend`. No speed figures are reported:
M3 is a correctness gate, and benchmarks belong to M5.

Adapters, from `cargo run -p bytelanes-wgpu --example adapters`:


**PCIe link.** Windows reports the GPU's own link
(`DEVPKEY_PciDevice_CurrentLinkSpeed` and `CurrentLinkWidth`) as speed code
4 (16 GT/s, Gen4), width 16. But the GPU sits behind a PCIe switch on the
card: the GPU endpoint connects to an AMD downstream switch port, then an
AMD upstream switch port, then the AMD root port (`1022:1483`). So that Gen4
x16 reading is the link inside the card, not the slot. Windows exposes no
link speed on the switch or root port. The slot link is therefore taken from
`docs/machines.md` (A520 chipset: PCIe 3.0 x16) and has not been measured.
See question 2.

## Open questions for Evan

1. **MSRV.**
   - wgpu 30 needs Rust 1.87, and the workspace declares 1.85.
   - `bytelanes-wgpu` now sets `rust-version = "1.87"` itself; the other
     crates stay on 1.85.
   - The alternatives are to raise the whole workspace to 1.87, or to pin an
     older wgpu.
   - Not checked locally with a 1.87 toolchain; built with 1.99.1.
2. **Confirm the slot link before M5 run files.** Every atlas run file has
   to record the PCIe link, and Windows can't read the slot link. GPU-Z's
   "Bus Interface" field, or AMD Software's "Bus Type", would show it, for
   example "PCIe x16 3.0 @ x16 3.0". Can you read one of those and confirm?
3. **GPU tests in CI.**
   - GitHub's runners have no GPU, so CI builds `bytelanes-wgpu` and the GPU
     tests print `SKIPPED` and pass.
   - The R7 evidence for this GPU is the local run above.
   - A self-hosted runner on the Ryzen would make it continuous. Do you want
     one? It would have to stay idle during pipeline benchmarks (M2, M6).
4. **Vulkan or DX12 for the atlas.** Both reproduce the reference exactly.
   Should M5 measure both, or pick one? I suggest both, as separate run
   files, since the cost of moving data in and out can differ between APIs.
5. **Speed is untuned.**
   - The backend submits and waits on each step of a program.
   - The CRC chunk pass reads a byte at a time.
   - Both are fine for a correctness gate but will understate the GPU in M5.
     I'd expect to tune them at the start of M5, before any atlas run. That
     changes no format and no results.

## Notes

- **Vectors checkout.** M1's note asked Windows checkouts made before
  `.gitattributes` to refresh `vectors/`.
  - My refresh command removed the vectors from the git index for a moment;
    I restored the index with `git reset -- vectors`.
  - `git ls-files --eol vectors` then showed no CRLF files in the working
    tree, and `git status` was clean.
  - The CPU vectors test passed before and after.
- **Golden cases need an empty backend.** `crypt/unknown-key` needs a
  backend with no keys loaded. The CPU test makes a new `CpuBackend` for
  each case, so the GPU test calls `clear()` between cases. With one shared
  backend, that case failed because a key from an earlier case was still
  loaded. It was a harness issue, not a GPU difference.
- **Input size limit.** Inputs and Vram buffers are limited by the device's
  maximum storage binding size, which is 2 GiB here. A larger input
  completes with `DeviceError` instead of running; the CPU reference has no
  such limit. No golden or random case comes close.
