## Built

### bytelanes-bench

- **`ops`:** checksum, encrypt, decrypt and filter, from 64 B × 4ⁿ up to
  256 MiB or at explicit `--sizes`. Each size runs on the CPU reference and
  on every hardware adapter.
- **`commitlog`:** one batch in flight, 1 to 1,048,576 generated 256-byte
  payment records per batch.
  - **Commit (write path):** two programs, a fraud-rule filter on the
    amount column and encryption of the records.
  - **Audit (read path):** a chained decrypt and filter on the device;
    only the indices come back.
- **`stream`:** throughput, with 16 batches in flight. The GPU runs with
  overlap off and on; the CPU reference runs on 1, 8 and 16 threads, one
  backend per thread.
- **Method:**
  - Everything goes through `ChannelBackend` submit and poll.
  - Each point runs at least 1 s and 5 repetitions, after warm-up.
  - Every completion is checked against the CPU reference.
  - Latency percentiles are recorded, along with CPU time spent on the work
    (process CPU minus the caller's polling).
- **Metadata:** each run file records machine, OS build, drivers, PCIe
  link, rustc, wgpu, the commit (clean or not) and the command.

### bytelanes-wgpu

Each change was measured before and after.

1. **One readback wait per program.** The result and its CRC come back
   together, straight into the host buffer.
2. **Pooled staging buffers**, for readback and for uploads of 64 KiB and
   more.
3. **Slicing-by-4 CRC-32C.**
4. **Pooled device buffers.** This fixes the 64 MiB slowdown; see the
   investigation below.
5. **Program overlap** (on by default; `WgpuBackend::set_overlap`).
   - The worker issues program *k+1* (all GPU work submitted, readback
     started) before it finishes *k*. A program that reads host bytes *k*
     writes waits for *k*.
   - A lone program behaves exactly as before.

**API changes (all to the strategy trait):**
- **Breaking:** `CopyingStrategy::new()` replaces the unit value.
- New provided methods on `BufferStrategy`, each with a default, so existing
  strategies keep working: `download_into`, `begin_download`,
  `finish_download` and `recycle`.
- New types `Readback`, `ReadRange` and `PendingDownload`.

### bytelanes CPU reference fix

`CpuBackend` copied every source into a new `Vec`, built every result in
another freshly allocated `Vec`, copied it into the destination, and
computed a CRC for every command (a completion reports only the last). A
probe measured AES-256-CTR on the Ryzen:

| Threads | Kernel alone | Through `CpuBackend` before | Through `CpuBackend` after |
| --- | --- | --- | --- |
| 1 | 6.55 GB/s | 1.88 GB/s | 5.32 GB/s |
| 8 | 18.2 GB/s | 4.06 GB/s | 10.5 GB/s |

The probe was a temporary example and is not committed.

Sources are now read in place, and AES writes straight into the destination.
Outputs and statuses are unchanged: the committed vectors replay, and the
props, FFT and GPU conformance suites pass. A new same-buffer test covers
source and destination in one buffer, in both directions.

## The filter slowdown at 64 MiB: diagnosed and fixed

- **Symptom:** in the first atlas runs, filter at 64 MiB was slower on the
  GPU than at 16 or 256 MiB, before and after tuning.
- **Finer sweep** (16 to 256 MiB, scratch run, not kept): a step, not
  noise. On Vulkan, filter went from 6.83 ms at 56 MiB to 17.0 ms at
  64 MiB; encrypt from 15.2 to 28.0 ms at the same sizes; checksum from
  12.1 ms at 96 MiB to 25.7 ms at 128 MiB. DX12 showed the same steps.
- **Pattern:** the step appears when the device buffers one program
  allocates pass about 128 MiB. Filter and encrypt cross it at 64 MiB with
  input plus output; checksum crosses it at 128 MiB with its input alone.
  CPU time barely moved, and both APIs were affected, which fits the
  allocator creating and freeing a fresh memory block on every call.
- **Fix:** pool and reuse device buffers. The same sweep afterwards, on
  Vulkan:
  - filter 64 MiB: 17.0 → 7.58 ms;
  - checksum 128 MiB: 25.7 → 16.4 ms;
  - encrypt 256 MiB: 120 → 68.1 ms.

  Every op is now linear in size. A repeat with 2 s series confirmed encrypt
  around 64 MiB is linear too (17.9 ms at 64 MiB); an apparent 23 ms point
  in the 0.5 s sweep was noise.
- **Safety check:** with the scratch clears disabled, the tests still pass,
  so no kernel reads scratch bytes it did not write. The clears stay as a
  safeguard.

## Results (from the run files; details in `atlas/crossover.md`)

| Workload | GPU faster (median latency) from | GPU uses less CPU from |
| --- | --- | --- |
| Checksum | never (≤ 256 MiB) | never |
| Encrypt / decrypt | never | 16 MiB |
| Filter | never | 64 MiB (DX12); 256 MiB (Vulkan, marginal) |
| Commit batch | never (≤ 1,048,576 transactions) | 65,536 (DX12); 262,144 (Vulkan) |
| Audit batch | 262,144 transactions | 262,144 |

- **Single ops:** at 256 MiB the CPU reference takes 9.74 ms for checksum,
  48.0 ms for encrypt and 23.7 ms for filter. Vulkan takes 31.4, 68.0 and
  29.6 ms. The GPU's only gain is CPU time: encrypt at 256 MiB costs
  25.7 ms of CPU through DX12, against 48.4 ms on the CPU.
- **Audit, 1,048,576 transactions:** 1.81 ms on Vulkan against 4.63 ms on
  the CPU, and 0.5 to 1.2 ms of CPU against 4.6 ms. Keeping a chain on the
  device is the one place the GPU wins outright.
- **Overlap** (16 batches in flight):
  - Commit: +24% on Vulkan and +23% on DX12 at 4,096 transactions per
    batch; +4% and +6% at 262,144.
  - Audit: +15% and +25% at 4,096; +23% and +29% at 262,144.
- **All cores against the GPU** (throughput):
  - Commit at 262,144: the CPU on 8 threads does 37.9 M txn/s; the best GPU
    does 14.1 M.
  - Audit at 262,144: the CPU on 16 threads does 509 M txn/s; the best GPU
    does 347 M.
  - The CPU stops scaling past 8 threads on large commit batches: 1.8× one
    thread, while CPU time per transaction rises from 47 to 205 ns, which
    points at memory bandwidth.
  - What the GPU offers is CPU time per transaction: 31 to 39 ns per commit
    and 2 ns per audit.

## Notes and caveats

- **CPU-time resolution.** Windows counts CPU time in scheduler ticks
  (about 15.6 ms). Large sizes have few repetitions, so their per-call CPU
  times carry about ±0.5 ms. The two filter CPU-time crossovers sit at that
  margin.
- **Superseded runs.** The first atlas runs (`…-untuned.json` from
  `fb80a1a`, and the unsuffixed files from `cc13614`) stay as the record. Their
  CPU columns are not valid comparisons; `crossover.md` says so.
- **Plan conflict.** The commit-log workload is not in the plan: the spec
  removed the transaction ledger in favour of `diagsteno`. Evan asked for it
  this session. It is a benchmark only.
- **Atlas naming.** Beyond `<date>-<op>.json`, the atlas now has
  `<date>-commitlog.json`, `<date>-stream.json`, the `-untuned` suffix, and
  `-2` for re-runs. `atlas/README.md` documents them.
- **CI runner autostart.** The scheduled task never fired after a reboot.
  It was replaced by a shortcut in the Startup folder (bytelanes README,
  "GPU CI").
