## Built

### bytelanes-bench

- **`ops`:**
  - Runs checksum, encrypt, decrypt and filter at 64 B × 4ⁿ up to 256 MiB.
    Each size runs on the CPU reference and on every hardware adapter
    (Vulkan and DX12 here).
  - Writes one run file per op.
- **`commitlog`:**
  - Batches of 1 to 1,048,576 generated 256-byte payment records.
  - **Write path:** two programs in flight per batch. One filters the amount
    column with a fraud rule (about 1% flagged). The other encrypts the
    records for the log; that completion's CRC is the segment CRC.
  - **Read path (audit):** one chained program. It decrypts an encrypted
    amount column into device memory, filters it there, and returns only
    the flagged row indices.
- **Method:**
  - Every program goes through `ChannelBackend` submit and poll, so GPU
    times include all transfers.
  - Each point runs at least 1 s and 5 repetitions, after 3 warm-up
    repetitions.
  - Every repetition's completion must equal the CPU reference's, or the
    run aborts.
  - Recorded per point: latency percentiles, and CPU time spent on the work
    (process CPU minus the caller's polling).
  - Two crossovers per op: latency and CPU time.
- **Metadata:** each run file records machine, OS build, GPU and driver per
  API, PCIe link, rustc, the locked wgpu version, the commit (and whether
  the tree was clean), the exact command, and a note.
- **Safety:** it refuses to run as a debug build, and never overwrites a run
  file.

### bytelanes-wgpu tuning

Measured before and after; both sets of run files are kept.

1. **One GPU wait per program, not two.** The final host result and its CRC
   come back in one readback, straight into the host buffer, with no
   intermediate `Vec` and no second copy. This adds
   `BufferStrategy::download_into` and `Readback`; the default implementation
   uses `download`, so other strategies keep working.
2. **Pooled readback staging.** Readbacks stop allocating fresh host memory
   that the OS has to zero.
3. **Pooled upload staging for inputs of 64 KiB and more.** Before this,
   `queue.write_buffer` allocated a staging buffer of the full input size on
   every call, which made 256 MiB inputs disproportionately slow. Smaller
   inputs keep `write_buffer`, which is cheaper there (measured).
4. **Slicing-by-4 CRC-32C** in the chunk pass, instead of byte at a time.

**Breaking:** `CopyingStrategy` is now a struct; construct it with
`CopyingStrategy::new()`.

## Results (from the run files; details in `atlas/crossover.md`)

| Workload | GPU faster (median latency) from | GPU uses less CPU from |
| --- | --- | --- |
| Checksum | 16 MiB (Vulkan); 4 MiB (DX12, marginal: 0.853 against 0.861 ms) | 4 MiB |
| Encrypt | 4 MiB | 1 MiB |
| Decrypt | 4 MiB | 1 MiB (Vulkan); 4 MiB (DX12) |
| Filter (u32, about 1% match) | 256 MiB. The GPU also wins at 16 MiB but loses at 64 MiB (17.6 against 16.8 ms), so by the definition the crossover is 256 MiB | 4 MiB |
| Commit batch | 16,384 transactions | 16,384 transactions |
| Audit batch | 262,144 transactions | 262,144 transactions |

What the numbers say:

- **Small work stays on the CPU.** Each GPU call has a fixed cost of about
  0.25 to 0.4 ms. At 256 KiB and below the CPU reference finishes every op
  in less time than that.
- **Commit, 1,048,576 transactions (256 MiB):**
  - Latency: CPU 145.8 ms (7.2 M txn/s); Vulkan 88.3 ms (11.9 M txn/s);
    DX12 99.8 ms (10.5 M txn/s).
  - CPU time per transaction: CPU 138 ns; Vulkan 42 ns; DX12 31 ns.
- **Audit, 1,048,576 transactions:**
  - Latency: CPU 4.74 ms; Vulkan 1.82 ms; DX12 1.99 ms.
  - CPU time per transaction: CPU 4.5 ns; Vulkan 1.0 ns; DX12 0.8 ns.
  - Chaining on the device, so that only the indices cross PCIe, is the
    largest relative win.
- **The tuning mattered.** Untuned, the GPU had no latency crossover for any
  single op or for the commit path. Tuned, encrypt and decrypt cross at
  4 MiB and the commit path at 16,384 transactions.
  - Encrypt at 16 MiB went from 10.0 ms to 4.98 ms (Vulkan).
  - Checksum at 256 MiB went from 93.1 ms to 40.9 ms (Vulkan).
  - Commit at 1,048,576 transactions went from 202.3 ms to 88.3 ms
    (Vulkan).
- **DX12 against Vulkan.** Latency is within a few percent at most sizes;
  Vulkan is ahead on the largest inputs. DX12 consistently uses less CPU
  time at large sizes (for example, checksum at 256 MiB: 14.9 against
  24.4 ms).

## Notes and caveats

- **The CPU reference uses one core.** A multi-core CPU baseline would have
  more throughput but the same CPU time per transaction. The CPU-time
  crossover is the figure that answers "does offloading free the CPU".
- **The CPU-time figures are coarse.** Windows updates thread and process
  CPU time at scheduler ticks (about 15.6 ms). Each series runs at least
  1 s, so per-repetition CPU times are means; small per-call CPU figures
  carry about ±0.1 ms of noise.
- **One program in flight.** The worker runs programs one at a time and
  waits for each. Pipelining (uploading the next batch while the current one
  computes) is not built. It would raise GPU throughput for streaming
  batches, but would not change the crossover, which is defined per call.
- **Filter at 64 MiB is slower on the GPU than at 16 or 256 MiB.** This
  showed up both before and after tuning, so it is not noise from one run.
  The cause is not investigated: possibly the per-call allocation of the
  64 MiB index buffer, or the extra wait for the match count.
- **Plan conflict.** The commit-log workload is not in the plan: the spec
  removed the transaction ledger in favour of `diagsteno`. Evan asked for it
  this session. It is a benchmark only, with no new crate or op.
- **Atlas naming.** Two names beyond `<date>-<op>.json`:
  `<date>-commitlog.json`, and `-untuned` for the kept baseline runs.
  `atlas/README.md` documents both.
- **CI runner autostart.** The scheduled task never fired at logon after
  the 2026-11-22 reboot. It was replaced by a shortcut in the Startup folder
  (bytelanes README, "GPU CI").
