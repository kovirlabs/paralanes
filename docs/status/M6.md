## Built

### stagelanes-pipe

- **`link::<T, N>()`:** a one-way stage-to-stage link.
  - It is an SPSC ring from `stagelanes-ring` plus a close flag.
  - A full link and an empty link are both busy-polled: no system call, no
    lock, no allocation.
  - Dropping the sender closes the link. The receiver sees the close only
    after it has received every item sent before it.
  - Tested.
- **`CorePlan::for_socket`:** picks cores from the topology, one logical
  CPU per physical core (its first SMT thread), in core order.
  - `take(n)` hands out cores and refuses more than the socket has.
- **`spawn_stage(spec, body)`:** starts a stage thread pinned to its core,
  at a `Priority`.
  - `ctx.ready()` ends start-up and starts counting the thread's
    allocations; `ctx.finish()` stops counting.
  - The `StageReport` gives allocations after ready, busy and idle polls,
    and any pinning or priority errors.

### stagelanes-mem: `CountingAlloc`

A global allocator that counts the allocations of threads that have
armed counting.

- The count lives in thread-local cells with constant initialisers, so
  counting itself never allocates.
- An integration test installs it as the global allocator and checks that:
  - an armed thread's allocations are counted;
  - a thread that never armed counts nothing;
  - an armed thread that does not allocate counts 0.

### stagelanes-bench

```
source -> parse -> worker x 4 -> sink      (cores 2,4,...,14; core 0 left to the OS)
   ^                              |
   +------- blocks returned ------+
```

- **Items:** 256-byte blocks from a `BlockPool` set up before the stages
  start.
  - Stages pass block handles over links, and the sink returns them to the
    source.
  - Stages reach a block only through header accessors, which count the
    bytes they touch and cannot reach the payload (R1).
- **Per-item work:** calibrated, 500 ns in parse and 4 µs in a worker, so
  the four workers are the bottleneck.
- **Single-core baseline:** the same work per item, done inline on one core.
- **Load:**
  - An unpaced run measures capacity first.
  - Then batches of 8 items are released at 50% and 90% of capacity, either
    evenly spaced (`--arrivals fixed`) or with random exponential gaps from
    a seeded generator (`--arrivals poisson`, the same sequence every run).
- **Latency** runs from an item's *scheduled* release to the sink, so a
  source that falls behind cannot hide delay.
- **Ideal queue:** the same arrivals fed through a zero-overhead model of the
  same pipeline at the measured capacity. Its latency is the queueing delay
  that the arrival pattern causes by itself.
- **Per stage:**
  - allocations after ready;
  - CPU time over wall time (a stage that blocked on a lock or a system
    call would fall below 1);
  - voluntary context switches (Linux only; Windows has no per-thread
    count);
  - bytes touched per item.
- **Options:** `--socket`, and `--pool-node` to place the pool on a NUMA
  node (for the Dell).
- **Run files** go to `atlas/runs/<machine>/<date>-pipeline.json` and are
  never overwritten. Each records the OS build, rustc, commit, exact
  command, configuration and every repeat.

What the runs show:

- **With evenly spaced arrivals and time-critical stage threads, latency
  holds at 90% load.**
  - p99 stays within 11% of p50.
  - The worst single item at 90% load took 65 µs.
- **At normal priority Windows preempts stage threads.**
  - Every normal-priority run has maxima of 1 to 3.5 ms.
  - In repeat 3 of `-pipeline-2` the source stage lost 1.5% of its CPU time
    (12.02 of 12.2 s).
  - At 90% load each millisecond of stall takes about 9 ms to drain, so p99
    reached 19 ms.
  - Time-critical priority stops this. This is the priority lever from the
    item 7 experiment, and here it works because the stall is preemption by
    other threads, not interrupts.
- **With Poisson arrivals the runtime adds almost nothing.**
  - p99 is within 0–9% of the ideal model, and p99.9 within 5% at
    time-critical priority (298.5 against 285.9 µs at 90%).
  - The 5.4× ratio is queueing theory: the ideal model scores 5.19×.
- **The pipeline beats one core at the same load fraction.**
  - Its p99 is 3.5× lower with fixed arrivals (10.6 against 37.3 µs at 50%),
    and 4.5× lower with Poisson arrivals at 90% (193.6 against 881.7 µs).
  - One core processes each batch of 8 items in sequence, so its latency is
    the whole batch.

## Open questions for Evan

1. **How should R2 be tested?** The spec says "p99 at 90% core utilisation
   is at most 3x p99 at 50%" but not with what arrivals.
   - **Evenly spaced arrivals** test the runtime alone: nothing queues below
     capacity, so any growth is overhead or interference. The pipeline
     passes at 1.04×.
   - **Random arrivals** add queueing delay that no runtime can avoid: a
     perfect zero-overhead pipeline scores 5.19×.
   - My recommendation:
     - Keep 3× for evenly spaced arrivals.
     - Add a second rule for random arrivals: p99 within 10% of the ideal
       queue model at each load. The Ryzen measures 4–9%.
   - This is a spec change and your call.
2. **Should stage threads default to time-critical priority?** On Windows,
   normal priority let the OS preempt a stage, and one run in three
   collapsed. Time-critical removed it.
   - `spawn_stage` takes the priority explicitly; the bench defaults to
     normal.
   - Raising it means a stage thread that spins can starve everything else
     on its core. Stage cores are reserved, so that is the intent.
   - On Linux it maps to `SCHED_FIFO`, which needs `CAP_SYS_NICE`.
   - Recommendation: make time-critical the documented default for stage
     cores, and leave the API explicit.
3. **Release 2 (`stagelanes` 0.1.0) is prepared, not merged.**
   - The `stagelanes` PR has the version bump, changelog and README.
   - Wait for question 1 and agent A's Dell run before merging.
   - The branch is based on `exp-windows-isolation` (stagelanes PR #2),
     because `spawn_stage` uses its `set_current_thread_priority`. Merge #2
     first.
4. **A reboot is pending.** It applies the interrupt-routing revert. Today's
   runs had device interrupts on CPUs 0–1, which is not the machine's
   normal state.
   - I can rerun the time-critical pair after the reboot, as a control.
   - That is about 6 minutes, and I'll do it when you say the machine has
     rebooted.
